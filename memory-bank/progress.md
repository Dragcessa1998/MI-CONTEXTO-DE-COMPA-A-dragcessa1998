## Proyecto avanzado: Supplier Directory (FastAPI) — oficial del syllabus

- **Supplier Directory — Lightweight Storage API** ✅ — primer proyecto del track Python: `services/api` (**FastAPI + TinyDB + Pydantic**, gestionado con **uv**). Modelo `Supplier` calcado del CONTEXT oficial de Nexova (Spain/USA, 9 categorías, `active`/`suspended`, regla **moneda↔país**, `rate_updated_at` generado por el sistema). Seeder `uv run seed` idempotente con los 15 proveedores del CONTEXT. Endpoints: POST/GET(+filtros país/categoría)/GET:id/PATCH rate/PATCH status/DELETE, errores 404/422 consistentes, CORS. Frontend: página **/suppliers** del backoffice (tabla, filtros sin recarga, alta con 422 inline, tarifa inline, activar/suspender, badge de estado y aviso de renovación <60 días). Verificado: seeder ×2, 22 checks de endpoints con curl, persistencia tras reinicio, `tsc` + `next build` OK.
- **Cierre de aceptación del Supplier Directory (12/08/2026)** ✅ — los modelos de entrada rechazan campos desconocidos y timestamps del sistema falsificados (`extra="forbid"`). Se añadieron **13 pruebas pytest** que cubren las 15 filas exactas e idempotencia del seeder, CRUD, filtros simples/combinados, reglas del CONTEXT, 404/422 y persistencia TinyDB tras reapertura; todas pasan. La UI se verificó contra la API real: filtro USA + Software ATS (1 resultado), edición/restauración de tarifa, activación/restauración de estado y validación inline del formulario vacío. `next build` continúa limpio. `npm audit` informa 3 vulnerabilidades high heredadas de Next.js/PostCSS/Nanoid; su única corrección propuesta salta a Next 16, por lo que se aplaza esa migración mayor al trabajo específico de rendimiento/seguridad.
- **AUTH-01 — autenticación y restricción de rutas (12/08/2026)** ✅ — `User` (solo credenciales) y `Profile` (nombre/contacto) viven en tablas separadas de TinyDB con relación uno-a-uno; servicio CRUD, roles cerrados, bcrypt, JWT HS256 con secreto y expiración de entorno, `get_current_user`, control owner/admin y respuestas sin hash. Se protegen las **6 rutas existentes** de `/suppliers`; token ausente, malformado, expirado o de usuario inactivo devuelve 401 y el acceso a otra cuenta devuelve 403. `POST /auth/login` sirve JSON al backoffice y `/auth/token` adapta el formulario OAuth2 de Swagger. Verificado con **26 pruebas** (13 de proveedores + 13 de auth) y recorrido manual real en `/docs`: registro 201 → Authorize → GET protegido 200.
- **Centralized Incident Manager (12/08/2026)** ✅ — modelo y API autenticada en `/api/incidents` con las 8 categorías, 4 sedes, 3 orígenes y ciclo de vida exactos de Nexova; filtros, detalle, 400 por campo, 404, 500 genérico y resumen completo (incluye ceros). El paquete Python en `packages/shared` concentra validación CSV, transformaciones y transiciones. `scripts/seed_incidents.py` cargó **96/100** registros válidos, reportó 4 inválidos sin PII y la segunda ejecución omitió los 96; resumen post-transformación: estados 27/56/13 y categorías 49/35/12. Backoffice `/incidents`: login JWT, métricas, formulario con sede resaltada, estados de carga/error/vacío, filtros y PATCH optimista con reversión. Una prueba real en navegador descubrió y permitió corregir la concurrencia de TinyDB mediante operaciones bloqueadas; **37 pruebas** pasan, incluida lectura paralela ×100, y `next build` genera 7 páginas correctamente.
- **Auditoría transversal de errores (12/08/2026)** ✅ — informe trazable en `docs/ERROR_HANDLING_AUDIT.md`. La Talent API ya no expone `err.message`: usa un contrato estructurado y un 500 genérico, con JSON inválido como 400. Los clientes Next.js normalizan red/HTTP/JSON sin mostrar status, rutas o mensajes técnicos; formularios limpian estados en `finally`, usan defaults y todos los errores ofrecen reintento/corrección/navegación. Ambos seeders validan entrada, escriben a stderr sin PII y retornan códigos 0/1. Añadidas pruebas de no filtración, archivos/cabeceras inválidos y fallo de TinyDB.
- **Containerización del monorepo (12/08/2026)** 🟡 — Dockerfiles Alpine/Node y Python/uv, un único contenedor UI para website + backoffice, FastAPI con reload, Compose con bind mounts, volúmenes de dependencias y red `nexova-dev`. El backoffice usa un proxy same-origin y el servidor Next comunica con FastAPI mediante `http://backend:8000`; secretos sólo por `.env` ignorado. `docker compose config`, requirements, builds y proxy vivo pasan; `compose up` y la evidencia de contenedores quedan pendientes porque el host no tiene daemon Docker/Podman.
